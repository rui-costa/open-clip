# ADR-005: Prompt-Defined LLM Pipeline Steps

## Requirement
Adding a new LLM step to the pipeline must not require code changes. Dropping a prompt into the config folder has to produce a working, schema-validated pipeline step with its own button in the UI.

## Decision
1. **Prompt file is the task**: every `backend/config/prompts/<NAME>.md` is a task. The file stem, lowercased, is the task name and therefore the pipeline step name (`CHAPTERS.md` -> step `chapters`).
2. **Schema is mandatory**: each task must have a JSON Schema at `backend/config/schemas/<name>.json`, or an explicit `schema` path in `backend/config/llm_tasks.json`. A task with no schema logs a warning and fails its step execution before any API call is made. A response that parses but violates the schema also fails the step, and the output is not persisted.
3. **Config is overrides only**: `backend/config/llm_tasks.json` is optional, keyed by task name, and carries only `template`, `schema`, `is_json`, `depends_on`, `auto_run`, and `result_adapter`. A config entry that names its own `template` consumes that prompt file, so it is not also auto-registered under its file name.
4. **Pipeline merge**: `pipeline.json` stays authoritative for the steps it declares. Discovered tasks missing from it are appended to `steps` and inserted into `execution_order` right after the last step they depend on, which is what makes the button appear.
5. **Placeholders are a closed set**: templates may only use the placeholders in `CONTEXT_PROVIDERS` (`transcript_text`, `word_map`, `project_name`, `highlights`, `video_metadata`). An unknown placeholder fails the step with the list of valid names. Providers resolve lazily, so a prompt pays only for the context it asks for.
6. **Results**: a task with no `result_adapter` stores its validated output in `Project.llm_outputs[<task>]` and is rendered generically in the UI. `highlights` and `metadata` keep their typed fields through named adapters in `RESULT_ADAPTERS`.
7. **One button for all of them**: prompt-backed steps are marked `llm: true` in the served pipeline config and collapse into a single "LLM Queries" control. Hovering previews the dropdown of tasks and their statuses; pressing the button pins it open so the rows can be clicked to run individual tasks. The collapsed button shows the worst status of the group, so a failed prompt is visible without opening it. Without this, every new prompt would widen the step row.
8. **Validation is in-tree**: `backend/src/infrastructure/schema_validator.py` implements the draft-07 subset the schemas use (`type`, `properties`, `required`, `items`, `enum`, boolean `additionalProperties`), so schema enforcement adds no runtime dependency.

## Justification
* **No code per prompt**: `LLMQuery` previously branched on `task_name` in five places, so every new prompt meant editing service code, the orchestrator, and two config files.
* **Fail loud, fail early**: schemas were declared in config but never loaded. Validating before persistence keeps malformed model output out of `metadata.json`, and resolving the schema before the API call avoids paying for a generation that cannot be stored.
* **Config drift**: deriving the step name from the prompt file name removes the second mapping (`extract_highlights` -> `highlights`) that had to be kept in sync by hand.
